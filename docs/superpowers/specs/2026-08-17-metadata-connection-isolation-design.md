# 元数据连接隔离修复设计

## 问题

文档上传接口使用独立 MySQL 连接原子写入文档、版本和索引任务，但 API 查询与后台索引 Worker 共用 `MySQLMetadataStore._conn`。该连接会保留 MySQL `REPEATABLE READ` 事务快照，并且 PyMySQL 连接不支持多线程并发使用。结果是新任务已提交，旧连接却暂时查不到，导致页面空列表和 Worker 误报“索引任务不存在”。

## 方案选择

### 采用：线程本地连接

`MySQLMetadataStore` 保留当前公开方法，将内部长期连接改为按线程创建和复用。API 线程和索引 Worker 线程不再共享同一个 PyMySQL 连接。每次普通查询完成后结束当前读事务，避免后续查询长期停留在旧快照。需要原子性的文档版本切换仍使用现有独立事务连接。

这个方案保留现有存储、SQL 表结构和业务接口，改动集中在连接生命周期。

### 不采用：上传后手工 `commit`

只能解决当前一个事务快照，无法解决 API 与 Worker 并发共用 PyMySQL 连接的根本问题。

### 暂不采用：引入第三方连接池

连接池更适合高并发生产环境，但会引入新依赖和更大改动面。本轮先修复正确性，不扩大范围。

## 数据流

1. 上传请求用独立事务连接写入文档、版本和索引任务并提交。
2. 上传请求把 `task_id` 放入内存队列。
3. Worker 线程使用自己的元数据连接查询已提交任务。
4. Worker 认领任务，顺序执行解析、分块、向量写入和版本激活。
5. 页面轮询使用 API 线程自己的连接，能看到 `queued -> parsing -> chunking -> indexing -> ready`。

## 错误处理

- 连接失效时只重建当前线程的连接，不影响其他线程。
- SQL 失败时回滚当前线程事务，不在失效连接上继续执行。
- 文档原子写入和版本激活的现有事务边界保持不变。

## 测试

- 回归测试证明不同线程获取不同连接，同一线程可复用连接。
- 回归测试证明独立事务提交后，Worker 能立即看到新任务。
- 运行元数据、异步索引、文档 API 与全量测试。
- 重启后端后观察当前 `queued` PDF 恢复为 `ready`，前端列表能稳定显示文件。

## 现场恢复补充

连接隔离修复生效后，Worker 能够找到原排队任务，但真实 PDF 产生 19 个子块，暴露 DashScope Embedding 接口单批最多 10 条的限制。为完成同一个上传索引目标，`_BailianEmbeddings.embed_documents()` 需按现有 `_EMBEDDING_BATCH_SIZE=10` 分批请求，并保持返回向量顺序与输入文本一致。

## 非目标

- 不替换 MySQL、Chroma 或 Redis。
- 不引入连接池依赖。
- 不修改前端上传交互。
- 不改变索引任务状态机和数据库表结构。
